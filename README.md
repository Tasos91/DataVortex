# DataVortex

Σωλήνας δεδομένων για διπλωματική: δέχεσαι **οποιοδήποτε JSON**, λες **ποια πεδία σε ενδιαφέρουν**,
και το σύστημα τα στέλνει σε Kafka ως Protobuf, τα αποθηκεύει σε TimescaleDB, και τα αναλύει με
ομαδοποίηση, κατάταξη και ανίχνευση ανωμαλιών — με διαφορετική μεταχείριση ανά τύπο δεδομένων.

```
                    ┌──────────────────────┐
  POST /upload ───► │  ingestion-service   │ ──► Kafka (Protobuf + Schema Registry)
  POST /stream      │        :8080         │         │
                    └──────────────────────┘         ▼
                                              ┌──────────────┐
                                              │  consumer    │ batch, DLQ, idempotent
                                              └──────┬───────┘
                                                     ▼
                                           ┌──────────────────┐
                                           │   TimescaleDB    │ hypertables + συνεχή
                                           │                  │ συγκεντρωτικά (1m→1h→1d)
                                           └────────┬─────────┘
                                                    │ (read-only)
                                           ┌────────▼─────────┐
                                           │   api-service    │ :8082
                                           └────────┬─────────┘
                                                    │ HTTP
                                           ┌────────▼─────────┐
                                           │ analytics-ui     │ :8085  ← εδώ κοιτάς
                                           └──────────────────┘
```

**Μόνο το `api-service` διαβάζει από τη βάση.** Το UI δεν έχει καν driver βάσης στο classpath, και
η σύνδεση του API είναι read-only επιβεβλημένη από τον server.

## Ξεκίνα σε τρία βήματα

```bash
docker compose up -d postgres kafka schema-registry prometheus grafana
bash run-all.sh                 # τα τρία services (logs στο logs/)
xdg-open http://localhost:8085  # το UI
```

| Τι | Πού |
|---|---|

## Στείλε δεδομένα

Δίνεις το JSON και λες ποια πεδία θέλεις να γίνουν μετρήσεις:

```bash
curl -X POST localhost:8080/api/v1/upload -H 'Content-Type: application/json' -d '{
  "sourceId": "gpu-farm",
  "topic": "ingest.ai", "createTopicIfMissing": true, "partitions": 6,
  "keyField": "$.host",
  "timeField": "$.ts",
  "payload": [{"ts": 1760000000000, "host": "gpu-1", "gpu_util": 87.5, "latency_ms": 42}],
  "fieldMappings": { "GpuUtil": "$.gpu_util", "LatencyMs": "$.latency_ms" }
}'
```

- `fieldMappings`: **όνομα πεδίου → διαδρομή στο JSON**. Υποστηρίζει `$.a.b`, `$.items[0].x`,
  `$['με κενά']`, και σκέτα ονόματα στηλών για CSV.
- `keyField`: ποιο πεδίο καθορίζει το partition — ίδιο κλειδί σημαίνει εγγυημένη σειρά.
- `timeField`: ο χρόνος του γεγονότος από τα ίδια τα δεδομένα (epoch ή ISO-8601).

Για μεγάλο όγκο υπάρχει `POST /api/v1/stream` με **NDJSON**: πρώτη γραμμή οι ρυθμίσεις, μετά μία
εγγραφή ανά γραμμή. Στη μνήμη βρίσκεται μία γραμμή τη φορά, άρα δεν υπάρχει όριο μεγέθους.

## Τι κάνει η ανάλυση

Δεν υπάρχει μία ανάλυση για όλα. Το κατάλληλο **προφίλ** επιλέγεται από τα ονόματα των πεδίων:

| Προφίλ | Αλγόριθμος | Τι κάνει διαφορετικά |
|---|---|---|
| `ai-telemetry` | k-means + ανθεκτική κλιμάκωση | ονομάζει τα καθεστώτα κατά φορτίο και ψάχνει ρητά «υψηλή καθυστέρηση **χωρίς** φορτίο» — βλάβη, όχι φόρτο |
| `weather` | k-means + **εποχική βάση ανά ώρα** | μια ζεστή νύχτα είναι ανωμαλία, ένα ζεστό μεσημέρι όχι |
| `generic` | **DBSCAN** με αυτόματο eps | δεν ξέρει πόσες ομάδες υπάρχουν και ονομάζει ρητά τα outliers |

Νέος τύπος δεδομένων = μία κλάση που υλοποιεί το `DataProfile`. Τίποτα άλλο δεν αλλάζει.

## Γιατί μένει γρήγορο όσο κι αν μεγαλώσουν τα δεδομένα

| Μετρημένο στο ίδιο μηχάνημα (i3-8100, 4 πυρήνες, όλα μαζί) | |
|---|---|
| Εισαγωγή 100.000 εγγραφών × 5 πεδία, μέχρι τη βάση | **21s** (4.756 εγγρ/s, 28.534 γραμμές/s) |
| Ερώτημα χρονοσειράς 12 ωρών | **3,2ms** από συγκεντρωτικό, 36ms από τα ωμά |
| Φόρτωση όλης της σελίδας | **20ms** (ένα request) |
| Ανάλυση 700 κουβάδων (clustering + ανωμαλίες) | **38ms** |
| Σελίδα 300 ωμών εγγραφών | **4,2ms** (όσο και η πρώτη) |

Τα τέσσερα που το πετυχαίνουν:
1. **Συνεχή συγκεντρωτικά** (`metric_1m → 1h → 1d`): το κόστος εξαρτάται από τους κουβάδες που
   ζητάς, όχι από τον όγκο. Κρατάμε `sum` και `sum_sq`, ώστε μέσος και τυπική απόκλιση να
   υπολογίζονται σωστά σε κάθε επίπεδο.
2. **Keyset pagination**, ποτέ `OFFSET`: η σελίδα 1000 κοστίζει όσο και η πρώτη.
3. **Το ML τρέχει πάνω σε χρονικούς κουβάδες**, όχι σε ωμές γραμμές: 10 εκατομμύρια εγγραφές σε
   24 ώρες δίνουν τους ίδιους ~600 κουβάδες με 10 χιλιάδες.
4. **Cache + ETag + ένα request** για όλη τη σελίδα, με παράλληλη συλλογή.

## Αξιοπιστία

- **Idempotent αποθήκευση**: πλήρες replay του topic δεν προσθέτει ούτε μία γραμμή (δοκιμασμένο).
- **DLQ**: ένα χαλασμένο μήνυμα πάει στο `dlq.ingest` και η ροή συνεχίζει — όχι ολόκληρο το batch.
- **Πέφτει η βάση;** Άπειρα retries αντί για DLQ: τα offsets δεν γίνονται commit, το Kafka κρατά
  τα δεδομένα, και η ροή συνεχίζει μόλις επανέλθει (δοκιμασμένο με τη βάση σβηστή για 25s).
- **Backpressure**: μικρός buffer και όριο ταυτόχρονων εισαγωγών (429) αντί να δεχόμαστε
  περισσότερα απ' όσα προλαβαίνουμε.
- **86 tests**, από τα οποία 24 integration (Testcontainers με πραγματική TimescaleDB, και
  service-to-service πάνω από πραγματικό HTTP).

## Ανάπτυξη

```bash
export JAVA_HOME=~/.jdks/corretto-21.0.2     # η default java είναι 11
./mvnw -q -o -pl api-service compile          # ένα module
./mvnw -q -o -pl analytics-ui-service test    # τα test ενός module
./mvnw -q install -DskipTests -pl common -am  # μετά από αλλαγή στο .proto
bash run-all.sh api                           # ένα service μόνο
```
